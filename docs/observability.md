# Phoenix observability and public read gateway

## Trace export

`createObserver({ endpoint, apiKey, spoolDir })` accepts every raw Pi JSON event synchronously and exports standard OTLP/HTTP protobuf in the background. Pass the full HTTP collector URL, normally `http://phoenix-internal:6006/v1/traces`; Phoenix documents that self-hosted HTTP endpoint and Bearer API-key authentication. A root `AGENT` span measures the session-level run through `agent_settled` or the service's synthetic `run_end`; assistant spans start at the extension's `before_provider_request` hook and end at authoritative `message_end`, while tools use `tool_execution_start`/`tool_execution_end`. Each source event is stored incrementally in completed `CHAIN` child spans (`pi.event`, or `pi.tool.output` for streamed tool text) beneath its owning AGENT/LLM/TOOL span, with task, run, and Pi session correlation. This allows raw events to reach disk and Phoenix before the parent run ends. Token counts come only from the finalized assistant message, avoiding streamed cumulative-usage double counting. Tool inputs, final model/tool outputs, and errors are retained. [Phoenix endpoint documentation](https://arize.com/docs/phoenix/resources/frequently-asked-questions/what-is-my-phoenix-endpoint), [Phoenix authentication](https://arize.com/docs/phoenix/self-hosting/features/authentication), [OpenInference LLM conventions](https://github.com/Arize-ai/openinference/blob/main/spec/llm_spans.md)

The pinned Pi extension forwards `{ type: "pi_provider_request", provider, model, payload }` from `before_provider_request`, after Pi has assembled the final protocol payload and immediately before headers/network. The observer retains that exact JSON payload as `input.value` when it fits the active-value budget, otherwise as reconstructible `pi_span_value` child events; it includes the actual system prompt, messages, and tool declarations but intentionally excludes request headers and the API key. The runtime integration test compares the forwarded payload with the local model server request body.

Completed spans are encoded as protobuf in `spoolDir` (the service uses `dataDir/trace-spool`). Each write uses a mode-0600 temporary file, flushes it, atomically renames it to `.span`, then syncs the directory; new directories use mode 0700. One observer owns a spool directory. These durability writes are synchronous and add filesystem latency to event handling. Files are removed only after collector acknowledgement. Startup replays pending files, and an unref'ed one-second timer retries while the process is idle. `close()` clears that timer, finalizes open spans, waits for export, and leaves failed deliveries on disk. HTTP failures, timeouts, or uncertain OTLP partial-success acknowledgements retain the batch. Delivery is at least once: a crash after collector acceptance but before deletion can resend the same trace/span IDs.

Exports contain at most 50 spans and 1 MiB of encoded payload, with a five-second request timeout. Directory scans and batches do not load the complete backlog into memory. Open spans retain at most 512 KiB of serialized input/output attributes before moving additional values into `pi_span_value` child events, with byte count and SHA256 references on the semantic span. Raw JSON larger than 32 KiB is split into lossless base64 fragments; reassemble `pi.event` values by `pi.event.id` and zero-based `pi.event.fragment`, decode base64, then parse the resulting UTF-8 JSON. `pi.event.fragments` supplies the expected count. Individual output chunks retain `tool.call_id`, `tool.name`, and `pi.output.sequence`; optional stream identity is retained as `pi.output.stream`. Sort by output sequence, then fragment index, to recover original tool text. Recently completed tool IDs (up to 1,024 per run) keep late chunks attached to their TOOL parent; unknown IDs fall back to the run parent with `pi.output.parent_missing=true`, retaining all data. For up to 1,024 recently closed runs, output arriving after the terminal event uses the original run parent and session correlation.

The default spool quota is 1 GiB. `retryMs`, `maxBatchBytes`, `maxActiveBytes`, and `maxSpoolBytes` can override these limits; use at least 64 KiB per export batch for raw fragments. Quota exhaustion, oversized spans, serialization errors, and filesystem failures emit explicit stderr errors without stopping task execution. These are observable data-loss boundaries, not a zero-loss claim. Terminal events release completed run/message/tool state even when persistence fails; finalization attempts each remaining semantic span independently and reports failures. Interrupted temporary writes remain on disk for inspection and count toward quota; they are not replayed as completed spans. Active semantic spans exist until finalization, so a process crash preserves their completed raw-event children but cannot reconstruct unfinished parent timing/status. `maxActiveBytes` bounds retained value bytes per semantic span; total active memory also depends on concurrent open runs/tools and transient serialization of the event supplied by Pi.

## Public read-only gateway

`createPhoenixGateway({ upstream, viewerKey })` returns a Node request listener. Expose this gateway publicly while keeping Phoenix itself and its collector on an internal network. The gateway discards caller authorization and cookies, injects only its configured Viewer API key, allows `GET`/`HEAD` for explicit UI, static asset, health, and read API paths, and allows `POST /graphql` only when the `graphql` parser proves every operation is a query. Authentication, user/settings, OAuth, MCP, collector writes, REST writes, GraphQL mutations/subscriptions, redirects, and unknown paths are denied. Phoenix documents that Viewer REST access is read-only and that trace upload is a forbidden write for Viewers. [Phoenix authentication and Viewer permissions](https://arize.com/docs/phoenix/self-hosting/features/authentication)

Configure the upstream with `PHOENIX_ENABLE_AUTH=True` and a strong `PHOENIX_SECRET`. Create separate keys: a system key for the internal collector and a Viewer user key for this gateway. Set `PHOENIX_DEFAULT_RETENTION_POLICY_DAYS=7`; Phoenix defaults to indefinite retention, and existing per-project policies can override the default, so verify every trace project in Settings → Data Retention. [Phoenix data retention](https://arize.com/docs/phoenix/settings/data-retention)

## Local Phoenix compatibility validation

On 2026-09-27, the implementation was exercised against `arize-phoenix==20.16.0` on Python 3.12.13, bound only to `127.0.0.1`. The isolated instance used authentication, generated ephemeral SYSTEM and VIEWER API keys, and a seven-day default retention policy. Key values stayed in mode `0600` ignored scratch files and were not logged.

The real collector accepted the observer's OTLP protobuf request and stored correlated `pi.run` and `pi.llm` spans. The stored LLM span contained the complete synthetic provider request, final output, 11 prompt tokens, 2 completion tokens, task/run/session fields, and raw Pi events. Phoenix's SQLite policy row was `{"max_days":7.0,"type":"max_days"}`.

The seven-day deletion path was also exercised with the same Phoenix version. The validation ingested two traces through the real authenticated collector, changed one trace and its spans to eight days old, and left the other recent. It then invoked Phoenix's actual `TraceDataSweeper._apply` path with the stored default `MaxDaysRule`, using Phoenix's database engine and transaction factory. Phoenix deleted the old trace and all its spans while retaining the recent trace and all its spans. A post-retention GraphQL query authenticated with the Viewer key and reported the single retained trace.

Phoenix's default policy cron is `0 0 * * 0`, so the daemon evaluates the seven-day threshold weekly at Sunday midnight UTC. Seven days is the deletion threshold rather than a continuous maximum age; a trace can remain for nearly another week before the scheduled sweep. The validation directly invoked the same policy application method instead of waiting for the weekly wall-clock boundary.

Retention isolation was checked against a separate SQLite task ledger created through this service's real `Store` schema. The ledger contained a task sentinel and remained byte identical across the Phoenix sweep; the sentinel fields were also queried afterward. This proves the validated Phoenix path targeted its own database and did not modify that application ledger. Production still needs distinct configured database paths and backup coverage to preserve this separation.

Through the gateway, Phoenix returned the UI root, a referenced JavaScript asset, and a GraphQL project query showing the ingested trace. A caller-supplied Authorization header was replaced by the configured Viewer key. GraphQL mutation, OTLP write, authentication, and user-management paths returned 403 without reaching the upstream. A direct OTLP write to Phoenix with the Viewer key also returned 403, proving the upstream role itself cannot ingest traces.

This validation covered HTTP responses from the real UI shell, one static asset, and the GraphQL read used to find the trace. It did not run a browser through every Phoenix UI route or validate TLS, a reverse proxy, distributed storage, or an externally reachable deployment. Before public rollout, run the pinned production image through the same probes and exercise the trace pages in a browser; add a read route only when that UI produces a specific denied request, then rerun all denial probes. Existing per-project retention policies can override the seven-day default and must be audited separately.

### Browser trace-page check

A subsequent Ego Lite check traversed Projects → default → pi.run → pi.llm through the gateway without a browser login. The detail drawer displayed the complete synthetic system/messages/tools input, `probe complete` output, 11/2/13 token counts, and task/run/session attributes. Evidence is in the task artifact `outputs/phoenix-viewer-trace.png`.

Provisioning a LOCAL Viewer requires completing its initial password change **on the private upstream** before issuing/using its gateway key. Otherwise the UI routes to the mandatory password-reset form even though GraphQL reads return 200. The private provisioning script now resets that initial password, signs in again, and then creates the key. Never allow public authentication or password mutations to work around this setup requirement. Write controls can remain visible in the upstream UI; the gateway continues to deny their mutations. Public network/TLS deployment and actual expiry of old traces remain separate acceptance steps.

The deployment provisioning script now explicitly patches the default policy to a seven-day cutoff with an hourly sweep. A fresh real Phoenix run accepted the GraphQL policy mutation and its persisted row was verified as `cron_expression="0 * * * *"`, `max_days=7`. This avoids the upstream weekly default; deletion still follows the next hourly sweep, rather than an exact per-span expiry instant. The old-trace deletion path has been validated as described above; public hosting remains unverified.

### Native bash output beyond Pi's model view

Pi limits the text returned to the model by its built-in bash tool. The extension streams `{ type: "pi_tool_output", toolCallId, toolName, sequence, data, rawBytesBase64?, stream? }` events. Each raw slice is at most 8 KiB; even invalid UTF-8 decodes below the observer's 32 KiB text limit. After reconstructing a fragmented JSON event, concatenate decoded `rawBytesBase64` slices by tool, stream and sequence to recover exact original bytes; `data` remains readable UTF-8 text. The observer stores these as ordered children, preserving failed-command output. Bash and query results are mode-0600 files in the task TMPDIR. `result.details.fullOutput` remains available only when both raw and decoded content fit 256 KiB; larger results carry `fullOutputPath`, `fullOutputBytes`, and `fullOutputSha256`. Query tool messages point to large artifacts instead of putting them into the model context. The observer never reads arbitrary file paths.

Each output stream stops its command at 64 MiB with an explicit error and retains the partial artifact; it never claims that a capped command produced a complete result. Query cancellation kills the adapter process group, with bounded cleanup of inherited output pipes. Extension-side query group registration allows the Pi supervisor to terminate these groups when Pi exits or is stopped. IPC forwarding observes stdout backpressure; a JSON line over 8 MiB stops the run explicitly, and diagnostic stderr retains a bounded 64 KiB tail.

Real Pi/Phoenix acceptance on2026-09-28 read back two bash spans (success and intentional exit3), each with exactly200010bytes andSHA2561b4c3737aeef6d6642735ab873f519db10bd08673761619fef78de55f2679e83. Provider payloads did not contain the fullOutput detail. This confirms the actual exporter/storage path beyond the native truncation threshold, rather than only checking a20KB fixture.

### Deployed retention audit (2026-09-28)

The running AnyDev Phoenix database contains one project (`default`) and one retention policy (ID 0). Its rule is `max_days=7`, with `cron_expression="0 * * * *"`; the project has no policy override. Phoenix 20.16.0 `TraceDataSweeper._apply` selects projects whose policy ID is null when applying default policy 0, confirming this project inherits the seven-day hourly policy. This verifies all projects present at audit time; audit again if project overrides are added.
