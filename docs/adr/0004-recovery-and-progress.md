# 恢复时继续原任务，已到期的等待直接推进

为减少系统中断造成的额外等待，恢复后已到期的限时异议流程直接推进，不要求先补齐断线期间的消息，也不重新提醒或追加等待。已持久记录的暂停、拒绝和方案失效仍然有效；此选择接受断线期间未收到的 Owner 干预可能未能及时阻止执行。

中断恢复沿用原任务、工作区、分支和已有 MR。先核对外部操作的实际结果，再执行缺失步骤，不能因为成功回执丢失就重复创建 MR 或重复推送；同一任务同时只允许一个执行器修改。

连续 3 次无进展后进入阻塞，在原任务群 @ 当前 Owner，说明失败原因、已尝试内容和需要补充的信息。收到新信息、环境恢复或明确重试指令后再继续；重启不清零重试记录。

无进展按一次完整 Pi 执行轮次判定，不按单次工具调用失败计数。没有新增有效证据、没有解决阻塞、修复或检查结果也未改善，才计为无进展；改换说法或重复运行相同命令不算进展。有实质进展时清零连续计数。

每轮执行默认最多 60 分钟，可配置；到期请求停止并保存可恢复状态，进入既有重试流程，不能为了保存状态无限等待。该时长是初始配置，后续按实际大仓构建耗时调整。

主服务按任务在 SQLite 中保留已观察到的工具内容指纹和 Git HEAD。只比较真实内容，忽略工具包装层的耗时、临时输出路径等元数据；交替重复已知结果、重启后再次读取已知结果都不能清零计数。新内容仍需执行器判断其调查意义，指纹去重本身不证明根因或修复有效。

工具结果新颖性必须同时得到执行器 progress=true 的有效进展声明，才允许清零计数；实际业务 HEAD 改变单独算作代码进展。大型落盘输出使用内容 SHA-256 去重，不把随机文件路径算作进展。此约束仍依赖执行器如实判断证据意义，不能把字节变化当作根因已确认。
