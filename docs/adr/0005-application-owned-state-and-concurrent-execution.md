# 应用管理任务生命周期，Pi 按轮次并发执行

告警应用持久保存任务、方案、Owner 指令、倒计时和检查结果，并据此判定执行权限和完成条件；Pi 负责调查、提出方案和调用工具提交结果，对话内容不直接覆盖任务状态。这样任务恢复和权限判定不依赖对话是否被压缩或执行器是否存活。

等待 Owner、CI 或人工处理时结束当前 Pi 执行轮次，保留会话和任务状态，释放执行位置。常驻应用接收企微消息、维护倒计时、检查外部结果，满足继续条件后恢复对应会话。

首版采用一个 TypeScript/Node.js 常驻主服务和按需启动的 Pi 子进程，不拆分为多个微服务。主服务负责企微连接与通知、SQLite 任务状态、倒计时、队列、子进程生命周期和只读看板接口；每个运行中的任务由独立 Pi 子进程在对应 worktree 中执行，并向主服务提交方案与结果。

等待时保存 Pi 会话后退出任务子进程；恢复时重新启动子进程并加载同一任务的会话和工作区。主服务持续接收消息并调度其他任务，单个 Pi 子进程异常由主服务记录并按恢复规则处理。Phoenix 作为独立观测服务运行。

首版支持多个不同任务并发执行，默认最多同时运行 4 个 Pi 执行任务，可配置；调查和修复共用这个上限，等待 Owner、CI 或人工处理不占执行位置。4 是初始配置，不是 Pi 自身限制或经过容量验证的结果；后续根据机器资源、模型额度和排队情况调整。每个任务仍只允许一个执行器修改。

每个任务使用独立 Git worktree、分支和 Pi 会话，运行时使用独立执行进程，统一复用宿主构建环境。此决定替代原先的每任务容器方案，以简化同一业务大仓在单机上的并发执行；worktree 只隔离代码工作区，不提供宿主权限沙箱。

临时文件和测试产物放入任务独立目录，测试端口和外部测试数据避免冲突；保留任务并发上限，并限制重型构建并发。暂停或中止时管理任务启动的子进程。未来出现工具链版本冲突、不可信代码执行或文件与网络权限隔离需求时，再引入任务容器。

新任务基于最新 master 创建独立 worktree 和任务分支。中断恢复沿用原工作区，不重新创建或自动重置基线。

任务完成 7 天后自动清理其 worktree；此期限从任务完成计算，不从创建时间计算，不适用于仍在等待、暂停或阻塞中的任务。任务记录与 Pi 会话独立保存，不能将 worktree 清理等同于删除任务历史。

不同任务相互无感知，分别调查、修复、测试并提交 MR；即使修改范围重叠，也不因此串行、等待、复用其他任务的修复或建立跨任务依赖。此决定替代此前的重叠修改串行规则。跨 MR 的修改冲突和合并协调由 Owner 介入处理，Agent 不自动比较其他任务的方案或 MR；如果本任务的 MR 检查报告冲突，则向当前 Owner 报告实际结果，不将未通过的必需检查标记为通过。

同一告警事件的重复消息仍由接入层去重并关联同一任务；这不要求不同任务的 Pi 执行器互相感知。各任务仅受全局资源并发上限和自身的单执行器约束。

首版不将专用的受控 Git 推送、MR 创建工具及配套凭据隔离作为必做项。方案等待、授权和暂停仍是应用与执行器必须遵循的流程规则，但不能将这些规则描述为能够强制阻止任意 shell 写操作的权限边界。
